# KathApp — Auditoria CTO (2026-05-11)

> Auditoria completa de tudo que existe HOJE no repositório, com foco em "está alinhado, conectado, funcionando" e em **estrutura para escalar com a stack atual**. Snapshot tirado lendo arquivo-a-arquivo, sem confiar em PRD/wiki. Sucede o snapshot de 2026-05-01.

## 0. Sumário executivo

**Estado geral: arquitetura excelente, várias áreas em produção sólida — MAS três P0 ativos quebram fluxos críticos (assinar plano, dashboard admin, race condition em afiliados) porque a refatoração de planos (`free/start/pro/vip` → `free/acesso/plano1/plano2/plano3/atleta`) foi feita só no DB e em parte do código; landing, checkout de assinatura, dashboard e Schema.org/JSON-LD ainda usam os tiers antigos.**

**Top 3 forças:**
1. **Modelo financeiro de classe enterprise** — `revenue_streams` + `wallet_credits` (FIFO atômico) + `commission_rules` + `commission_allocations`, com RPCs `compute_commissions`, `spend_wallet_cents`, `credit_wallet_cents`, `decrement_stock_batch`. Pouquíssimos SaaS solo têm isso.
2. **Webhook Asaas robusto** — token timing-safe, idempotência via `webhook_events` PK, 5xx em erro de handler (Asaas reentrega), roteamento por `externalReference` para 3 fluxos (mensalidade/loja/estética), alimentação automática de revenue streams + cashback + comissões.
3. **Disciplina de desenvolvimento codificada** — `HANDBOOK.md` e `CLAUDE.md` capturam regras inegociáveis; CI bloqueia em type-check + lint + test + npm audit; env vars validadas em runtime com `requiredInProduction()`; design system com tokens semânticos.

**Top 3 riscos imediatos:**
1. **P0 — Assinar plano pago está QUEBRADO** (`/api/checkout/subscribe/route.ts:69` aceita só tiers antigos `start/pro/vip` que não existem mais). Receita de assinatura = R$ 0 até corrigir.
2. **P0 — Dashboard admin retorna zero** para todos os planos atuais (`admin/actions.ts:354-356` consulta `plan_tier='start'|'pro'|'vip'`). Kath olha o painel e parece que ninguém assinou.
3. **P0 — `schema.sql` consolidado está dessincronizado** com as migrations aplicadas. Quem rodar `schema.sql` num novo ambiente terá CHECK constraint antigo de plan_tier + faltarão 12+ tabelas (plans, team_members, revenue_streams, wallet_*, monthly_usage, estetica_*, moto_events, challenges, plan_templates, webhook_events).

**Top 5 ações de maior impacto imediato (Sprint 0, 1–3 dias):**
1. Trocar enum aceito no `/api/checkout/subscribe` e em todo cliente que chama esse endpoint (`subscribe-button.tsx`).
2. Migrar contagens do dashboard admin de slugs literais para `getActivePlans()` dinâmico.
3. Refatorar `(public)/page.tsx` `PricingSection` + `jsonLd` para consumir `getActivePlans()` (server fetch).
4. Trocar `/api/affiliate/click` para chamar `rpc('increment_affiliate_clicks', ...)` (RPC já existe no schema base — só não está sendo chamado).
5. Regenerar `supabase/schema.sql` consolidado a partir do estado atual do banco em prod (`pg_dump --schema-only`) e regenerar `lib/supabase/types.ts` via `supabase gen types`.

**Potencial de crescimento com a stack atual: alto.** O modelo financeiro suporta 0→10k assinantes pagos sem reescrita. Os bottlenecks reais não são técnicos — são (a) os P0 acima, (b) ausência de webhook Clerk para sync de delete/email, (c) Sentry frontend, (d) cobertura de testes <5%, (e) audit log de mudanças sensíveis. Stack pinada (Next 15.5, React 19, Supabase, Clerk v7, Asaas, ioredis, web-push) é adequada até pelo menos 50k MAU sem precisar adicionar serviços.

## 4. Estrutura para escalar com essa stack (0 → 10k usuários pagos)

A stack atual (Next 15 + Vercel + Supabase + Clerk + Asaas + Redis Railway + web-push) **suporta tranquilamente 10k MAU pagos sem trocar nenhum serviço**. O que precisa mudar é processo, observabilidade e domínios de negócio que ainda não foram modelados. Em ordem.

### 4.1 Sprint 0 (3 dias) — Estanque os P0s

Sem fazer isso, qualquer outra coisa é em cima de fluxos quebrados. Ordem:

1. **P0-1 e P0-2** primeiro (corrigem assinar plano + dashboard) — mesma natureza de bug (tier enum hardcoded).
2. **P0-5** (landing/JSON-LD) — depois que server fetch de `getActivePlans()` estiver pronto em (1) e (2), reusar.
3. **P0-4** (`increment_affiliate_clicks` RPC) — 5 linhas.
4. **P0-3** (regenerar `schema.sql` consolidado e `types.ts` via Supabase CLI) — esta é a fundação para os P1s.

### 4.2 Sprint 1 (1 semana) — Confiabilidade financeira

Dado que o produto monetiza, fluxo de dinheiro precisa ser blindado.

1. **P1-1** (PIX manual fallback bloqueado em prod) — risco direto de receita silenciosa.
2. **P1-5** (Sentry server real instalado) — sem isso, nada na §4 abaixo é observável.
3. **P1-6** (Asaas retry/backoff) — reduzir falhas transitórias virando 5xx pro usuário.
4. **P1-2** (single source para onboarding) — corrige loop potencial.
5. **P2-2** (Coupon use rastreia por user) — `coupon_uses` table existe mas nunca recebe row.
6. **Adicionar testes de happy path para `/api/checkout/subscribe` e `/api/loja/checkout`** — depois de corrigi-los, blindar.

### 4.3 Sprint 2 (1 semana) — Observabilidade e operações

1. **P2-6** Sentry frontend + DSN próprio para client (sourcemaps upload no build).
2. **PostHog ou Plausible** para product analytics (decida: PostHog se quiser feature flags + session replay, Plausible se quiser leve/privacy-first).
3. **P2-3** webhook Clerk para `user.deleted` + email change.
4. **P2-5** Audit log de mudanças sensíveis (`plan_tier`, `price_cents`, `commission_allocations.status`, `orders.status`).
5. **Runbook em `docs/runbook.md`**: como responder a Asaas indisponível, Supabase saturado, Redis fora, Clerk fora, deploy ruim (rollback Vercel), customer querendo cancelar reembolso, fraude de cupom etc.
6. **Healthcheck público com Better Uptime / UptimeRobot** apontando para `/api/health` — alertas via push/email/Slack pro Erick.

### 4.4 Sprint 3 (2 semanas) — Estrutura para escalar tráfego

Quando começar a fazer marketing pago / orgânico forte:

1. **Caching de leitura no Supabase**: planos `getActivePlans()` já tem TTL 60s. Aplicar mesmo padrão em `getWorkouts()` para listas longas. Considerar `next.config` `experimental.cacheComponents` quando estabilizar no Next 15.x.
2. **Image optimization**: ✅ já correto. Garantir todos os assets de produto/avatar/og usam `next/image` (auditar `(public)/page.tsx` que usa `<img>` na linha 418 do mockup — trocar para `<Image>`).
3. **Edge runtime em rotas estáticas** (sitemap, robots, health) — adicionar `export const runtime = "edge"` quando seguro.
4. **CDN warmup** para landing + fitness/[id] (Vercel já faz). ISR `revalidate: 3600` em sitemap e landing se conteúdo mudar.
5. **Streaming UI** com Suspense para chat e dashboard.
6. **Rate limit por IP além de por user** em rotas públicas (subscribe, push subscribe) — atualmente é só por userId.

### 4.5 Sprint 4–6 (1–2 meses) — Crescimento do produto

Features que extraem mais do produto sem trocar stack:

1. **Webhook receiver Clerk** para `user.deleted` (LGPD compliance + dados órfãos).

6. **Push notification UX**: mount do `usePushSubscribe` no `(app)/layout.tsx` com prompt **após 2ª sessão** (não no primeiro login — taxa de aceite cai para 5%).
7. **Notification center** in-app: já tem `notifications` table + `notification-bell` component — confirmar que está conectado ao realtime do Supabase.
