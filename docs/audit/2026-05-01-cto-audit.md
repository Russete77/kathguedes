# KathApp — Auditoria CTO consolidada (2026-05-01)

> Snapshot técnico de uma auditoria abrangente do projeto KathApp (Next.js 15 + Clerk + Supabase + Asaas, em produção). Cobre backend, frontend, database, fluxos de negócio, segurança e operações. Documenta achados com severidade e plano de correção. Para regras de desenvolvimento (como NÃO errar), ver `docs/HANDBOOK.md`.

## 0. Sumário executivo

- **Estado geral:** production-ready com reservas. Arquitetura sólida, segurança operacional bem encaminhada, RLS amplo, fluxos principais (assinatura, loja, estética, consultoria) funcionando.
- **Riscos críticos imediatos:** (1) `webhook_events` sem RLS expõe histórico financeiro; (2) race conditions em estoque/affiliate clicks/coupon; (3) webhook Asaas pode silenciar falhas; (4) buckets de Storage sem RLS visível; (5) divergência `price` (decimal) vs `price_cents` (int).
- **Gap de produto crítico:** modelo financeiro **não suporta múltiplas origens de receita nem comissões para a equipe**. Hoje, dashboard só vê receita de loja; assinatura/estética/consultoria invisíveis. Não há `team_members`, `revenue_streams` nem `commission_allocations`.
- **Dívida visível:** cobertura de testes <1%, hook `usePushSubscribe` órfão, admin layout integralmente client component, `requesting_user_id()` referenciada mas não criada, downgrade de plano bloqueado por UI.

## 3. Fluxos mapeados (resumo)

- **Assinatura:** `/planos` → `subscribe-button` → `POST /api/checkout/subscribe` → cria customer + subscription Asaas → retorna PIX/QR/boleto/cc → user paga → webhook `PAYMENT_CONFIRMED` → atualiza `profiles.plan_tier` + `subscription_status`. VIP dispara criação automática de `consultations`.
- **Loja:** `/loja` → carrinho client → `POST /api/loja/checkout` (recalcula preço com desconto por plano + decrementa estoque) → `/api/loja/payment` (Asaas PIX 1x) → webhook → `orders.status=paid` → admin gera label envio.
- **Kath Estética:** `/kath-estetica/servicos` → `/agendar/[serviceId]` → `RPC get_available_slots` → `POST /api/estetica/bookings` (recalcula preço + valida slot + checa loyalty) → `POST /api/estetica/bookings/[id]/payment` (Asaas) → webhook → `status=confirmed`. Programa fidelidade: 4 fotos aprovadas/mês = 5ª lavagem grátis.
- **Consultoria:** auto-criada para VIP → user preenche anamnese → admin monta plano (templates ou livre) em `plan-editor` → `status=in_progress` → entrega → `status=delivered`. Conteúdo SEMPRE in-app (nunca PDF).
- **Cupons/Afiliados:** RLS gating por `required_plan`; clicks_count e uses_count incrementados via RPC.
- **Chat VIP:** Realtime Supabase, RLS bloqueia INSERT se `plan_tier != 'vip'`. Admin responde em `/admin/chat`.
- **Onboarding:** força preenchimento via middleware (`metadata.onboarding_completed`).

## 5. Modelagem proposta — receita unificada + comissões

```sql
-- Receita por origem
create table public.revenue_streams (
  id uuid primary key default gen_random_uuid(),
  type text not null check (type in ('assinatura','loja','estetica','consultoria')),
  user_id text not null references public.profiles(id),
  amount_cents int not null check (amount_cents > 0),
  reference_id text,            -- order_id | booking_id | asaas_payment_id
  asaas_payment_id text,
  status text not null default 'confirmed' check (status in ('pending','confirmed','refunded')),
  created_at timestamptz not null default now()
);
alter table public.revenue_streams enable row level security;
create policy revenue_admin on public.revenue_streams for all to service_role using (true) with check (true);
create index idx_revenue_type_created on public.revenue_streams(type, created_at desc);

-- Equipe e roles
create table public.team_members (
  id uuid primary key default gen_random_uuid(),
  clerk_user_id text unique,    -- opcional: vincular a Clerk
  email text unique not null,
  full_name text not null,
  role text not null check (role in ('owner','manager','consultant','moderator','affiliate')),
  default_commission_pct numeric(5,2) not null default 0.00,
  pix_key text,
  bank_account jsonb,
  is_active boolean not null default true,
  created_at timestamptz not null default now()
);

-- Regras de split por origem (pode ser por role ou por membro)
create table public.commission_rules (
  id uuid primary key default gen_random_uuid(),
  source_type text not null check (source_type in ('assinatura','loja','estetica','consultoria','afiliado')),
  team_member_id uuid references public.team_members(id),
  role text,                     -- alternativa a team_member_id
  pct numeric(5,2) not null,
  applies_from timestamptz not null default now(),
  applies_to timestamptz,
  is_active boolean not null default true
);

-- Alocações concretas por transação
create table public.commission_allocations (
  id uuid primary key default gen_random_uuid(),
  revenue_stream_id uuid not null references public.revenue_streams(id) on delete cascade,
  team_member_id uuid not null references public.team_members(id),
  pct numeric(5,2) not null,
  amount_cents int not null,
  status text not null default 'draft' check (status in ('draft','approved','paid','failed')),
  paid_at timestamptz,
  payout_reference text,
  created_at timestamptz not null default now()
);
create index idx_alloc_member_status on public.commission_allocations(team_member_id, status);
```
